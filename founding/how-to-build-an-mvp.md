# How to Build an MVP

If you have a product idea and want to test whether people will actually use it, you do not need to build the complete product first.

> The goal is not to build a smaller version of the final product. It is to build **enough to test your most important assumptions**.

An [**MVP (Minimum Viable Product)**](what-is-an-mvp-in-software-development.md) is the smallest useful version of a product that lets you test your core idea with real users.

## Building an MVP

### 1. Start with the problem

Define the problem before defining the features.

Ask:

* Who has this problem?
* How are they solving it today?
* What makes the problem worth solving?
* What assumption about the customer or market are you trying to test?

> A clear problem makes it easier to decide what belongs in the MVP.

### 2. Define the smallest useful version

List the features you think you need, then remove everything that does not directly support the core use case.

For example, an appointment-booking MVP might only need:

* Create an account
* View available times
* Book an appointment
* Receive confirmation

It probably does not need advanced analytics, complex customization, or a referral system yet.

The goal is not to build a smaller version of the final product. It is to build **enough to test your most important assumptions**.

### 3. Decide who will build it

Once you know what you need to test, decide how the technical work will be done.

Depending on the product, you might work with:

* A small development team
* A technical co-founder or a full-stack software developer

Choosing the right technical person can be as important as defining the MVP itself.

See [How to Find a Technical Co-Founder](https://chatgpt.com/g/g-p-6a7839dbc6f08191b93f41935a85363f-gitbook/technical-founder/how-to-find-a-technical-cofounder).

### 4. Build for learning, not completeness

The first version should make the core workflow usable from beginning to end.

Then put it in front of real users.

Measure what happens:

* Do users understand the product?
* Do they complete the main action?
* Where do they get stuck?
* Do they come back?
* What do they actually ask for?

> These answers should influence what you build next.

## Common MVP mistakes

Many MVPs fail for reasons that have little to do with technology.

#### Building too much

Adding features feels like progress, but it can delay the moment when you learn whether the product is useful.

#### Building before validating the problem

A technically polished product can still fail if the underlying problem is not important enough.

#### Treating the MVP as the final product

An MVP is an experiment. Requirements will change once real users interact with it.

#### Optimizing for technology instead of learning

Choosing sophisticated architecture or infrastructure too early can consume time without improving the experiment.

#### Ignoring what happens after launch

Launching is not the end of the MVP. The useful part is what you learn from actual usage.

## What to learn from an MVP failure

A failed MVP is not necessarily a failed product.

The important question is **what failed**.

If users do not use the product, possible explanations include:

* The problem was not important enough.
* The target customer was wrong.
* The solution was difficult to understand.
* The product did not solve the problem well enough.
* The acquisition strategy did not reach the right users.

Do not automatically respond by adding more features. First determine which assumption was wrong.

### The key principle

An MVP is **not** about building as little software as possible.

It is about **learning as much as possible with the smallest useful product**.

> Start with the problem, identify the assumption you need to test, build only what is necessary, and let real users determine what comes next.
